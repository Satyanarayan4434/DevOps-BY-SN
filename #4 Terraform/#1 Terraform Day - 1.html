Infrastructure As Code

Infrastructure as Code, or IaC, means describing cloud infrastructure in files instead of creating it manually from a console.

Concept

Manual Infrastructure

  • Open AWS Console.
  • Click through pages to create VPCs, subnets, EC2, IAM, and security groups.
  • Repeat the same steps for every environment.
  • Risk: missed settings, undocumented changes, hard rollback.

Infrastructure As Code

  • Write desired infrastructure in files.
  • Review the change before applying it.
  • Reuse the same code for dev, test, and prod with different values.
  • Benefit: repeatable, reviewable, version-controlled infrastructure.

Repeatability

The same file should create the same intended infrastructure again and again.

Reviewability

Infrastructure changes become pull requests or commits, not hidden console activity.

Collaboration

Teams can discuss infrastructure through code, comments, approvals, and history.

Beginner Translation

Think of Terraform code as a recipe. The recipe does not cook by itself, but it clearly tells Terraform what ingredients to use and what final dish AWS should prepare.

Why Terraform?

Cloud providers have their own IaC tools, but Terraform became popular because one workflow can manage many platforms through providers.

Big Picture
ToolWorks Best WithBeginner Takeaway
AWS CloudFormationAWS resourcesPowerful inside AWS, but not a universal multi-cloud workflow.
Azure ARM/BicepAzure resourcesGreat for Azure, but tied to that provider ecosystem.
TerraformAWS, Azure, GCP, Kubernetes, GitHub, and many moreLearn one workflow and use providers to talk to many APIs.

Declarative Style

You describe the desired final state. Terraform figures out what actions are needed to move from the current state to that final state.

Plan Before Apply

terraform plan gives a preview. This is one of Terraform's most important safety habits for learners and teams.

Terraform Does Not Replace Cloud Knowledge

Terraform can create AWS resources, but you still need to understand what those resources mean. Day 1 correctly stresses VPC, subnet, AMI, key pair, EC2, and security group basics.

Setup Options

You can learn Terraform locally or in a cloud development environment. The best setup is the one that lets you practice safely and consistently.

Environment

Option A: Local Machine

  • Install Terraform CLI.
  • Install AWS CLI if you want CLI-based credentials.
  • Use VS Code or another editor.
  • Store projects in a clean folder and avoid committing secrets.

Option B: GitHub Codespaces

  • Use a browser-based dev environment.
  • Good for learners who do not want heavy local setup.
  • Still protect AWS keys carefully.
  • Destroy cloud resources when finished.

Install Terraform

Use the official Terraform install page for your operating system. After installation, run terraform version to confirm the CLI is available.

Prepare AWS Access

Create an IAM user or role with permissions appropriate for a lab. Avoid using root account keys. Prefer short-lived or limited permissions when possible.

Configure Credentials

Use aws configure, environment variables, or another approved credential method. Never paste actual keys into main.tf.

Create A Project Folder

Start with a clean directory containing main.tf. Terraform stores downloaded provider plugins under .terraform after initialization.

HCL Structure

Terraform files use HashiCorp Configuration Language. HCL is designed to be readable, so focus on the block structure first.

Syntax 
terraform {
  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 5.0"
    }
  }
}

provider "aws" {
  region = "us-east-1"
}

resource "aws_instance" "day1_demo" {
  ami           = "ami-xxxxxxxxxxxxxxxxx" # region-specific example only
  instance_type = "t2.micro"

  tags = {
    Name = "terraform-day-1-demo"
  }
}

Block

A block has a type, optional labels, and a body. Example: resource "aws_instance" "day1_demo" { ... }.

Argument

An argument sets a value inside a block. Example: instance_type = "t2.micro".

Provider Source

hashicorp/aws tells Terraform where to download the AWS provider from during terraform init.

Tags

Tags are AWS labels. They help you identify cost, owner, project, and purpose later.

HCL Reading Notes

Once the block structure feels familiar, the next skill is reading configuration safely before running commands.

Read First

AMI IDs Are Not Universal

An AMI ID depends on AWS region and date. Do not copy an old AMI blindly. Choose a current AMI from your target region before creating an instance.

Beginner Reading Trick

Read a resource block as a sentence: "Create one AWS instance named day1_demo with this AMI, this instance type, and these tags."

Questions To Ask

  • Which provider will this use?
  • Which AWS region will receive the request?
  • Which resource type is being created?
  • Which values are hard-coded placeholders?

Values To Treat Carefully

  • Account IDs and ARNs.
  • Security group rules.
  • Subnet, VPC, and AMI IDs.
  • Any value that might reveal a secret.

Reading Before Running

Never run a Terraform file just because it is short. Short configuration can still create public resources, open network access, or spend money.

AWS Authentication

Terraform does not magically own your AWS account. It needs credentials, then the AWS provider uses those credentials to call AWS APIs.

Security

Safer Patterns

  • Use AWS CLI profiles or environment variables.
  • Use least privilege for lab users.
  • Rotate/delete temporary learning keys after practice.
  • Use IAM roles where possible in real teams.

Avoid These Mistakes

  • Do not commit access keys.
  • Do not hard-code keys in main.tf.
  • Do not use root account access keys.
  • Do not share screenshots that reveal credentials.
# preferred beginner check
aws configure
aws sts get-caller-identity

# Terraform can then use the configured AWS credential chain.

Secret Rule

If a value can log in, create infrastructure, delete resources, or spend money, treat it as a secret. Never include it in this note, GitHub, screenshots, or messages.

EC2 Mini Project

The first project launches an EC2 instance. The Terraform syntax is short, but the AWS choices behind it matter.

Project

Inputs You Must Know

  • Region: where the instance will run.
  • AMI: the operating system image.
  • Instance type: CPU/memory size such as t2.micro.
  • Subnet: the network location inside a VPC.
  • Key pair: SSH access option for Linux instances.
  • Security group: firewall rules for inbound/outbound traffic.

Beginner-Safe Defaults

  • Use a free-tier eligible instance type if your account qualifies.
  • Use a non-production AWS account or sandbox.
  • Tag every resource with project and owner.
  • Run terraform destroy after practice.
  • Review the plan before applying anything.

What Terraform Is Doing

Terraform sends a request to AWS: create an EC2 instance with the settings in the resource block. AWS creates the real object and returns identifiers. Terraform stores those identifiers in state.

Project Code Walkthrough

This sample is intentionally conservative. Replace placeholders with current values from your own AWS region and account before any real lab run.

main.tf 
terraform {
  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 5.0"
    }
  }
}

provider "aws" {
  region = "us-east-1"
}

resource "aws_instance" "day1_ec2" {
  ami           = "ami-xxxxxxxxxxxxxxxxx" # choose current AMI for your region
  instance_type = "t2.micro"
  subnet_id     = "subnet-xxxxxxxxxxxxxxxxx"
  key_name      = "your-existing-key-pair-name"

  tags = {
    Name      = "terraform-day-1"
    Owner     = "Satyanarayan Sen"
    ManagedBy = "Terraform"
  }
}
Line/BlockPurposeBeginner Check
terraformDefines required provider plugins.Did terraform init download the provider?
provider "aws"Selects AWS and region.Is the region where your AMI and subnet exist?
aws_instanceDeclares the EC2 instance.Do all IDs match your account and region?
tagsAdds labels to the AWS resource.Can you recognize this lab resource later?

Do Not Paste This Blindly

The AMI, subnet, and key pair values are placeholders. A wrong region or missing key pair can cause errors, and an open security group can create risk. Learn the AWS concepts before applying.

Running The First Workflow

A clean workflow gives you confidence. The command order matters because Terraform needs setup, review, action, and cleanup.

Terminal 
# 1. Enter the project folder
cd terraform-day-1

# 2. Initialize providers
terraform init

# 3. Preview the changes
terraform plan

# 4. Apply only after reviewing the plan
terraform apply

# 5. Clean up lab resources when finished
terraform destroy

When Plan Looks Good

The plan should say Terraform will create the expected resource. For Day 1, that usually means one EC2 instance and any related resources you explicitly defined.

When Plan Looks Wrong

Stop. Fix the configuration, region, credentials, or IDs first. The whole point of plan is to catch surprises before AWS changes.

CommandCloud Resources Changed?Typical Beginner EmotionBest Habit
initNo"Did it install?"Read provider download messages.
planNo"What will happen?"Read every create/update/delete line.
applyYes"Now it is real."Confirm only after review.
destroyYes"Clean up costs."Verify the resource is gone in AWS.

Apply And Destroy Are Real Actions

This note documents the commands, but it does not run them. Use a controlled lab account and verify every plan before confirming.

Understanding State

State is Terraform's memory. It maps your code to real cloud resources and helps Terraform know what changed.

State

Why State Matters

  • Tracks resource IDs.
  • Helps Terraform detect drift.
  • Connects local names to cloud objects.
  • Supports planning future changes.

Beginner State Safety

  • Do not manually edit state files.
  • Do not commit state if it may contain sensitive data.
  • For teams, use a remote backend with locking.
  • Keep Day 1 labs simple and isolated.

Simple Mental Model

Your code says what you want. AWS has what really exists. State is Terraform's notebook that connects the two.

Cleanup And Cost Control

Learning cloud tools is fun until forgotten resources generate charges. Day 1 should end with cleanup discipline.

Safety

Always Destroy Lab Resources

After practice, run terraform destroy from the same project folder and confirm the result in the AWS Console. Deleted infrastructure cannot serve traffic, but it also stops avoidable lab spending.

# cleanup workflow
terraform plan -destroy
terraform destroy

# optional verification ideas
aws ec2 describe-instances --filters "Name=tag:Name,Values=terraform-day-1"
aws sts get-caller-identity

Before Destroy

  • Confirm this is only a lab project.
  • Check you are in the correct folder.
  • Check you are using the intended AWS account.
  • Read the destroy plan.

After Destroy

  • Refresh the EC2 console.
  • Look for leftover resources.
  • Check billing if you experimented beyond EC2.
  • Remove temporary access keys if no longer needed.
